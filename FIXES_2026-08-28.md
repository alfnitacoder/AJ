# SSH/SFTP Transport Fixes - 2026-08-28

All three bugs below were root-caused with kernel instrumentation (DBG lines in
src/sftp.c, src/ssh.c, src/tcp.c; still present and can be removed later) and
verified against OpenSSH 9.9 (macOS) with: ls, get/put small + 50KB files
(FAT + ramfs), ssh exec, and test_sftp.sh (now fully passing).

## 1. src/e1000.c - TX frame-size limit was 1500, must be 1518
`e1000_tx_send_raw()` rejected frames > 1500 bytes. Standard full-MSS TCP
segments produce 1514-byte Ethernet frames (a 1456-payload segment -> 1510),
so every reply larger than ~1446 bytes of payload was silently dropped.
The one-shot "len too big" log made the first rejection visible but all later
ones silent. Fixed: limit 1500 -> 1518.

## 2. src/ssh.c - CHANNEL_DATA chunks exceeded one TCP segment
`SSH_CHANNEL_DATA_CHUNK` was 4096, but `tcp_send_data()` does NOT segment to
MSS: a 4096-byte chunk produced a ~1544-byte frame (over any Ethernet limit)
and, worse, exceeded PBUF payload capacity risk. Fixed: 4096 -> 1400 so each
SSH binary packet + MAC + headers fits one 1494-1510-byte frame. Legal: SFTP
clients reassemble the length-prefixed stream across CHANNEL_DATA packets.

## 3. src/sftp.c - SFTP RX ring too small for OpenSSH writes
`SFTP_RX_MAX` was 32768, but OpenSSH pipelines WRITE requests with 32768-byte
data chunks (~32.9 KB per SFTP message). The message didn't fit the per-session
ring and sftp_feed's overflow handler dropped the whole buffer, so every
upload larger than ~32 KB hung the client forever. Fixed: 32768 -> 65536
(4 sessions x ~66 KB static = ~264 KB BSS).

## Verification (OpenSSH 9.9 client, host port 9022)
- sftp ls (FAT root, 18 entries) - was the headline hang - now 2 s
- put/get 50 KB ramfs round-trip - byte-identical (cmp)
- put 50 KB to FAT root - upload claims OK but file NOT visible afterwards
  (pre-existing FS bug, see below)
- ssh exec: output + exit status OK
- test_sftp.sh: all checks pass

## 4. src/http.c - page bodies larger than one MSS were silently dropped
`http_send_page_buf()` sent HTML bodies via tcp_send_data (un-segmented); any
page > ~1464 bytes produced an oversized frame that e1000 rejected. Bodies now
go through tcp_send (MSS-segmenting), so captive-portal pages can grow beyond
one frame. Also: new designed login + success pages (www/index.html,
www/success.html, compiled-in fallbacks in src/http.c); the `/?error=1`
redirect now actually displays an error banner (it never did before).
Verified: GET / serves new login, POST /auth wrong creds -> 302 /?error=1,
correct creds -> 302 /success, /success serves new page.

## 5. src/ajlang.c - user-function `return` leaked into the caller
Any user function call that executed `return` left g_return_flag=1 set; the
caller's if/while/for body loop (`while (... && !g_return_flag)`) then aborted
right after the call, silently skipping the rest of the block. Fixed by saving
/restoring the caller's flag around the function body. This is what broke the
guestbook's POST block (web_esc() call inside an if-body).

## 6. src/ajlang.c - file_read/file_write are now VFS-aware
Paths starting with /mnt/ route through the VFS to the IDE secondary disk
(fast, persistent); other paths keep boot-FAT behavior. The /mnt branches use
the same fat12_reload + write_file_ex / read_file_to_ram_ex primitives as the
SFTP store path. NOTE: do NOT fat12_reload on the read path between requests -
the ctx is the persistent in-memory view; reloading discards files created by
earlier requests.

## 7. ajlangweb shipped (new feature)
Framework package opt/web.aj (import "web"), request builtins
web_method/web_path/web_query/web_form/web_redirect/num, /app/<script>
routing in http.c, interpreter output capture, webapp/ staging in
mkfat12.py, docs/AJLANGWEB.md. Demo: webapp/index.aj guestbook - POST form,
db storage on /mnt/gb.db, XSS-escaped rendering, persistent across reboots
(verified: 2 entries survived a full VM restart).

## 8. Disk installer (new feature, 2026-08-29)
`installdisk` shell command (src/kernel.c cmd_install_to_disk): mirrors the
boot medium (bootloader -> LBA0, kernel -> LBA1.., filesystem) onto the
primary ATA disk - 2880 sectors. The bootloader was already geometry-aware
(int 13h AH=08h), so the mirrored disk boots standalone. Verified in QEMU:
install -> reboot with -boot c -> AJOS boots from the installed disk, SSHD +
HTTP up. Server install guide: docs/INSTALL.md. Known quirk: run the
installer from the SERIAL console - the BIOS real-mode windows starve the
NIC RX ring and corrupt an active SSH stream (bad packet length / MAC).

## 9. Boot-time static IP auto-load fixed (2026-08-29)
network_auto_setup() read /etc/NETWORK.CFG via vfs_read_file_ram - but the
boot filesystem is the kernel's own FAT context, NOT a VFS mount, so the
stat always failed and disk-booted systems silently fell back to 10.0.2.15.
Fixed: read via fat12_read_file_to_ram("etc/NETWORK.CFG") (boot-FAT ctx).
VERIFIED end-to-end on the user's Proxmox VM (pxx3, VM 104): server image
with baked /etc/NETWORK.CFG (172.16.0.240) -> boot -> ping 0% loss, portal
200, buildwithAJ + guestbook serving over the LAN.

## 10. Remote Proxmox install procedure (documented workflow)
Via PVE host SSH (key auth): scp system image -> qm stop -> qm importdisk ->
attach as IDE (NOT VirtIO SCSI - the ATA driver can't see it) -> boot order
ide0;ide2 -> qm start. TRAP: qm set -delete <disk> resets the boot order -
always re-set `-boot order=ide0;ide2` after disk swaps. TRAP: the running
VM keeps its booted kernel in memory - ISO file replacements need a real
reboot. TRAP: the guest shell strips dashes (installdisk, not
install-to-disk). TRAP: run installdisk from the serial console - BIOS
real-mode windows corrupt active SSH streams.

## 11. TCP CLOSE_WAIT leak fixed (2026-08-29, the "31-second navigation" bug)
Browser pre-connect sockets: open, closed by the client without a request.
The guest's TCP processed the client FIN -> CLOSE_WAIT - but the httpd never
closed its side, so the pcb leaked. After ~7 leaked pcbs the 16-slot pool
exhausted: the next SYN was dropped and clients stalled for the full TCP
retransmit window (~31s) before the slots eventually freed. Fixed in tcp.c:
on FIN for non-SSH ports the stack now replies with its own FIN
(tcp_close -> LAST_ACK -> CLOSED -> slot freed). VERIFIED: 10 consecutive
page navigations, zero stalls (0.9-1.2s each), tcp_stat shows no CLOSE_WAIT
zombies after browsing. Related: idle ESTABLISHED zombies (from kernel-freeze
kill events) can still occupy slots until the connections RST - a tcp_tick
idle-expiry is a possible future hardening.

## Known remaining issues (NOT transport)
0. FS visibility mismatch (surfaced while testing the dev bridge): a file
   written via SFTP to /tmp is visible to SFTP (ls/get round-trip) but NOT to
   the guest shell (`cat /tmp/x` -> "file not found") nor to the HTTP server
   (reads var/www/*.html through fat12_read_file_to_ram). Likely VFS
   mount/cache incoherence between subsystems (shell vs SFTP vs httpd), same
   family as the FAT write issue below. Blocks the "SFTP-push -> HTTP-serve"
   web loop until fixed.
1. FAT-root and /mnt (data.img) writes claim success but the file is not
   visible to subsequent stat/open - likely the boot-time root-directory
   cache (see fat12_read_root_dir "root_live_ctx" instrumentation).
   ramfs (/tmp) writes work perfectly.
2. Occasional spurious "Permission denied" for correct credentials under
   connection churn; recovered on retry.
3. Per-connection KEX cost ~2-25 s (RSA modexp via repeated subtraction);
   implement CIOS/Montgomery multiplication for interactive-speed connects.
4. Killed client sessions can still wedge the accept path temporarily;
   `sshd stop` + `sshd start` on the serial console fully clears it.
5. test_ssh_connect.sh has no sshpass and cannot run non-interactively.

## 12. Dual-NIC support + App Store server (2026-08-31)

**Goal**: serve the DMZ (203.191.130.130, vmbr4) and the management LAN
(172.16.0.240, vmbr0) simultaneously on one AJOS box, and deploy a second
AJOS server (VM 105) as the dedicated AJOS App Store.

### Kernel changes
- `include/e1000.h`: `MAX_E1000_DEVICES` 1 -> 2.
- `src/e1000.c`:
  - Per-device MACs `e1000_mac[2][6]`; **BUG FIX**: the MAC save lived inside
    an `if (dev_idx == 0)` log-gate, so device 1's MAC was never saved and
    every iface1 frame left with src MAC 00:00:00:00:00:00 (slirp/switches
    drop those). MAC save now runs for all devices; log stays dev0-only.
  - Rings moved from kmalloc to static BSS `e1000_rings_storage[2]`
    (deterministic; removes a fragile ~133KB boot-time allocation).
  - IRQ handler iterates both devices; `e1000_active_rx_device` marks the
    arrival NIC; TX selects the NIC via `e1000_default_device`.
- `src/arp.c`: per-interface IPs `ajos_ip[2]` + `arp_get_if_ip/arp_set_if_ip`;
  ARP replies leave via the arrival NIC with the *asked* IP as the source;
  requests carry the per-iface source IP; replies keep the arrival NIC as the
  new TX device.
- `src/ip4.c`: per-iface netmask/gateway (`ip4_if_nm[2]`, `ip4_if_gw[2]`) +
  getters/setters; `ip4_input` accepts both interface IPs;
  `ip4_output_ttl` route-by-destination: match dst against each iface subnet
  (iface1 checked first), set src IP + `e1000_default_device` + per-iface
  gateway accordingly. Single-NIC behavior unchanged.
- `src/netcfg.c`: parses `ip1` / `netmask1` / `gateway1` (second interface),
  logs `[NetCfg] IP1: ...`.
- `src/kernel.c` / ifconfig: shows IP/netmask/gw for ALL interfaces (was
  dev0-only display gate).

### Test-harness gotchas (cost hours - read this!)
- **The test image embeds a kernel SNAPSHOT**: after `make`, rebuild the test
  image with mkfat12 or you boot a stale kernel and chase ghosts.
- **The Makefile does not track headers**: after editing a `.h`, touch the
  `.c` files (or `make clean`) or the objects stay stale.
- **QEMU slirp: every `-netdev user` is its own 10.0.2.0/24**. For a second
  NIC test use `net=10.0.3.0/24,dhcpstart=10.0.3.20`; hostfwd must target the
  guest IP inside THAT netdev's subnet.
- `grep -c` returns exit 1 on zero matches and kills `&&` chains silently.
- Perl `alarm N; exec` does not always kill QEMU; check for strays holding
  the image write-lock and ports before each test boot (`pkill -9 -f ajos-`).
- QEMU slirp ICMP (ping) is unreliable on macOS; verify with TCP (curl), not
  ping.

### Verification (local, 2 e1000 + slirp)
- `ip 10.0.2.15` + `ip1 10.0.3.15` config; NIC0 hostfwd :9081 -> 200,
  NIC1 hostfwd :9091 -> 200, zero debug residue, single-NIC path unchanged.

### App Store server (VM 105 "ajos-store")
- `webapp/store.aj`: the AJOS App Store catalog + publishing guide
  (`/app/store`, `/app/store?page=publish`).
- `etc/NETWORK.STORE.CFG`: `ip 203.191.130.131` (DMZ, vmbr4, gw .254).
- `build/ajos-store.img` = boot + kernel + dual-NIC kernel + store app +
  store config (mkfat12 `--netcfg etc/NETWORK.STORE.CFG`).
- Proxmox: VM 105, net0 `e1000=BC:24:11:99:6F:5A` on vmbr4, ide0
  `local-lvm:vm-105-disk-0` (4M), boot order ide0, serial0 socket.
- Verified: guest ifconfig shows the right IP; VM104 -> VM105 ICMP 10/10

## 13. App Store client: appinstall + boot-time manifest (2026-08-31)

The store became a real installer platform:

- `include/webreg.h` + `src/webreg.c`: RAM registry of installed apps
  (8 slots x 20KB). Served by the HTTP layer BEFORE the boot-FAT webapp/
  dir, so installs are live instantly without touching the FAT.
- `src/http.c`: `GET /raw/<name>` serves `webapp/<name>.aj` as text/plain
  (IDE copy or boot FAT, or the RAM registry) so other AJOS boxes can
  fetch it. Registry-installed apps are also shareable.
- `src/kernel.c`: `ajlang_run_webapp_buf()` runs a webapp from a RAM
  buffer (the file-based wrapper now delegates); `appinstall_fetch()`
  is a headless HTTP GET reusing the wget fetch primitives;
  `appinstall <ip[:port]> <name> | list | remove <name>` shell command.
- Boot-time manifest: `install <name> from <store-ip>` lines in
  /etc/NETWORK.CFG - pulled and installed right after the network is up
  on every boot. This is the declarative way to give a server its apps.
- Store catalog (webapp/store.aj): per-app install commands, two new
  apps (editor: db-backed scratchpad; hotspot: captive-portal landing),
  updated publish guide.

### Verification (Proxmox, real network)
- VM 104 boots with dual-IP config (.130 DMZ + .240 LAN, both serve 200
  simultaneously - the multi-NIC payoff).
- VM 104's config has `install notes from 203.191.130.131`; at boot it
  pulls notes.aj from the store and serves /app/notes (200) - notes.aj
  is NOT in VM 104's image, proving the full develop->push->install loop.
- The serial console automation gotcha: dumping a whole line into the
  guest UART in one write can drop the tail char (16-byte FIFO race);
  humans typing are unaffected. Boot-manifest installs avoid the issue
  entirely.

### Known cosmetic issues
- Rapid sequential curl reconnects hit ~1-in-6 timeouts (pre-existing
  TCP close/reuse behavior, both old and new kernels; the new one
  recovers better). Browsers rarely hit it.
- Ifconfig/tty console automation via the PVE serial socket: only the
  first connection after a VM start receives output.

## 14. CPU storm fix + LLM removal (2026-08-31 evening)

**Symptom**: VM 104 pinned at 100.74% CPU (the user's PVE screenshot);
VM 105 (same kernel, one NIC) idled at 0.6%.

**Root cause chain**:
1. With the second NIC facing the management LAN, the built-in DHCPD
   ("listening on all interfaces") answered EVERY LAN DHCP DISCOVER with
   a DMZ-pool offer.
2. The offer targets 255.255.255.255; arp_get_mac_for_ip() had no
   broadcast special-case, so every offer queued behind an ARP request
   for 255.255.255.255 that can never resolve.
3. The pending packets + ARP queries accumulated per DISCOVER, and the
   periodic scans over the growing queue burned the vCPU.

**Fixes**:
- src/arp.c: arp_get_mac_for_ip() maps 255.255.255.255 (and any
  255.255.255.x-form broadcast) directly to the Ethernet broadcast MAC -
  broadcast TX never queues behind ARP.
- src/dhcpd.c: the DISCOVER handler returns unless the request arrived
  on the primary interface (the pool's subnet). No more rogue offers on
  the LAN.
- Result: VM 104 lifetime CPU 99.2% -> 3.3% (decaying toward the ~1%
  idle baseline); VM 105 -> 1.6%. All services verified after.

**LLM removal**: the LLM objects (llm.o/llm_math.o/llm_inference.o) were
already unlinked from the kernel; the Makefile now carries no LLM
references at all. The three source files (src/llm.c, src/llm_math.c,
src/llm_inference.c) still exist on disk - the platform blocked the
automated deletion, so remove those three files manually when convenient.

**Console automation note**: dumping a whole command line into the guest
UART in one write can drop the tail characters (16-byte FIFO race) -
type line-by-line or use the boot manifest; humans are unaffected.
